## 0) الفجوة المعمارية المركزية (مشتركة عبر كل الموديولات)

هذه ليست فجوات متفرقة بل **عيب معماري واحد** يتكرر:

| # | الفجوة | الدليل | الأثر |
|---|--------|--------|-------|
| A1 | **الصلاحيات client-side فقط وتفشل مفتوحة** | `can()` يرجع `true` لو `PERMISSIONS_CACHE=null` (`:9966`)، وتحميلها داخل try/catch عند الإقلاع (`:20742`) | أي فشل تحميل = صلاحية كاملة |
| A2 | **RLS الأساسية `using(true) with check(true)`** | `security-phase-b.sql:46-49` على users/role_permissions/overrides/meetings/tasks/maintenance/quality | أي مستخدم مسجّل يقرأ/يكتب أي صف عبر API مباشرة |
| A3 | **لا فرض لانتقالات الحالة** | كل الموديولات: `update({status})` بلا فحص الحالة الحالية | أي حالة ← أي حالة عبر PostgREST |
| A4 | **لا حماية للسجلات النهائية** | لا حظر تعديل على completed/closed/executed/cancelled في أي موديول | إعادة فتح صامتة، تلاعب بالمكتمل |
| A5 | **الهوية مأخوذة من العميل** | `created_by/inspector_id/sender_id/requester_id/branch_id = CURRENT_USER.*` (localStorage) | انتحال الفاعل والفرع عبر API |
| A6 | **الصلاحية على مستوى الصفحة فقط (view/manage)** | `can(section,'manage')` بت واحد يجمع add/edit/delete | لا تمييز إنشاء/تعديل/حذف |
| A7 | **لا سجل تدقيق بقيم قبل/بعد** | لا جدول audit موحّد؛ timelines نصية بلا قيم | لا إثبات «من غيّر ماذا» |

**الحل المعماري (يُبنى مرة ويُطبَّق على الكل):**
- `pilot-01-foundation.sql`: جدول `pilot_audit_log` + تريجر تدقيق عام + دوال تتبع. ✅
- `pilot-02..06`: RLS حقيقية مقيّدة بالفرع/القسم/الدور عبر `current_app_user_id()/current_app_role()`، + تريجرز حارسة لانتقالات الحالة والحماية النهائية، + تحقق Server-side.
- تعديلات الواجهة: إزالة الأزرار الصامتة، حرّاس `can()` داخلية للدوال العامة، وقف عرض/نسخ كلمة المرور.

> ⚠️ **قيد حرج على الـRLS:** تفعيل RLS صارمة يعتمد على `auth.uid()` عبر `current_app_user_id()`. المستخدمون الذين لم يُرحَّلوا بعد إلى Supabase Auth (لا `auth_id`) سيُحجبون. لذلك تطبيق RLS على Production **مرهون بترحيل Auth** (موديول 7) ويجب اختباره على Staging أولًا. كل ملفات RLS موسومة `REQUIRES SUPABASE STAGING`.

## 1) الاجتماعات

**موجود:** إنشاء/عرض/تعديل، حضور ومعتذرون، محضر (رفع ملف)، ربط قرارات/مهام، فحص إغلاق يتطلب أسباب تأخير للمهام (`:14283`).
**فجوات:**
- حذف جماعي للاجتماعات بلا حارس دور (`:13393`, `:13009`) — يعتمد على RLS الوهمية.
- لا حظر تعديل/تغيير حالة على `closed/cancelled` (`:13969`, `:14292`).
- زرّا «حفظ كمسودة» و«إرسال لاحقًا» كلاهما يكتب `status:'scheduled'` — **لا حالة مسودة فعلية** (`:13865`).
- **باگ مؤكد:** «إزالة كل الفلاتر» تستدعي `renderMeetingsTable()` غير المعرّفة (الصحيح `renderMeetingsTableBody`) → ReferenceError (`:13216`).
- حالة `done` يتيمة (في التفاصيل لكن خارج الفلاتر/KPI).
- جدول الأعمال (`meeting_agenda`) **مسار ميت** — دوال stub فارغة (`:13573-13575`).
- المرفقات على bucket `maintenance` عام (روابط عامة).
**الحكم:** PARTIALLY READY — STAGING SQL REQUIRED.

## 4) الصيانة

**موجود:** طلب→فحص→عروض→مقارنة→مالية→إصلاح→استلام→إغلاق، Timeline، 13 تقرير، معدات، صيانة وقائية، موردون، أصول فرع.
**فجوات:**
- انتقالات **UI-gated فقط**؛ RLS `using(true)` → أي حالة عبر API. تكلفة قابلة للتعديل بعد الاعتماد بلا سجل جديد.
- مراحل **ناقصة:** «بدء الإصلاح» صريح، **التحقق من جودة التنفيذ**، **إعادة الفتح عند فشل الإصلاح** (`closed` نهائية).
- الاعتماد الأولي بلا سجل معتمِد/سبب مستقل. `current_owner_id` معروض لكن **لا يُكتب أبدًا** (ميزة ميتة).

- صور الفحص/الإصلاح **حقول URL نصية** لا رفع فعلي.
- تعارض: `severity` الافتراضي `'normal'` بينما الواجهة `low/medium/high/critical`.
**الحكم:** PARTIALLY READY — STAGING SQL REQUIRED.

- حذف نهائي `users.delete()` cascade بتأكيد عميل فقط.

**الحكم المُلزَم:** `INTERNALLY READY — AUTH STAGING APPLICATION REQUIRED` (لا يُدّعى اكتمال الترحيل قبل تطبيقه واختباره على Staging).

## الافتراضات المنطقية المسجّلة
1. **الصيانة:** «التحقق من الجودة» يُنفَّذ كحالة `awaiting_quality_check` بين الإصلاح والاستلام، يعتمدها دور جودة/مدير فرع (اعتمادًا على تسلسل القسم IV في التكليف). «إعادة الفتح» تنشئ سجل تدقيق وتعيد الحالة إلى `in_progress`.
2. **الجودة:** فصل المهام = من ينفّذ الإجراء التصحيحي لا يعتمد إغلاقه؛ يُفرض بتريجر يمنع `verified_by = corrective_action_owner`.
3. **الطوارئ:** توحيد الحالة على `processing_status` كمصدر وحيد (`new→in_progress→closed`) وإلغاء ازدواج `status`.
4. **الأدوار:** نموذج الصلاحيات الحالي بلا بُعد فرع؛ النطاق الفرعي يُفرض عبر RLS بمطابقة `users.branch_id` لا بتغيير `role_permissions` (تجنّبًا لتغيير سياسة إدارية جوهرية دون طلبك).
5. **حذف password_plain من Production ممنوع** — المسارات الجديدة فقط تتوقف عن كتابته/عرضه؛ العمود يبقى حتى ترحيل Auth الفعلي.
