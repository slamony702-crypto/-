# 🔴 B1 — إزالة `password_plain` والانتقال لـSupabase Auth

## أين المشكلة الآن (تحققت منها في الكود)

| الموقع | المشكلة |
|--------|---------|

## الوضع الحالي المُربِك (مهم تفهمه)

النظام **مزدوج حاليًا:**
- بعض المستخدمين لديهم حساب Supabase Auth حقيقي (مشفّر) — هؤلاء آمنون
- لكن **نفس الباسورد يُخزَّن أيضًا** في `password_plain` كنسخة نصية
- المستخدمون الجدد يُنشأون بـ`password_plain` فقط أحيانًا، ثم يُنشأ لهم Auth لاحقًا

يعني: **الأساس السليم موجود جزئيًا** (Supabase Auth) — المطلوب حذف النسخة النصية والاعتماد على Auth فقط.

## نقاط قرار تحتاج رأيك (لا أقرر فيها) 🚦

| القرار | الخيارات | توصيتي |
|--------|----------|--------|
| **D-B1-1:** المستخدمون الحاليون بلا حساب Auth | (أ) إنشاء حساب Auth لكل واحد + إرسال رابط "تعيين كلمة مرور" — (ب) إجبارهم على "نسيت كلمة المرور" عند أول دخول | (أ) — أنظف تجربة |
| **D-B1-2:** شاشة "عرض كلمة المرور" للأدمن | تُحذف نهائيًا (الأدمن لا يرى كلمات مرور أبدًا) — بدلها زر "إرسال رابط إعادة تعيين" | حذف — هذا معيار صناعي |
| **D-B1-3:** توقيت الحذف | (أ) حذف العمود فورًا بعد الترحيل — (ب) إيقاف الكتابة أولًا لفترة، ثم حذف العمود لاحقًا | (ب) — أأمن، على مرحلتين |

## خطوات التنفيذ (بالترتيب، على Staging)

### المرحلة 1أ — إيقاف الكتابة الجديدة (كود فقط)
1. استبدال كل `INSERT ... password_plain` بمسار Supabase Auth:
   - `sb.auth.signUp()` أو `sb.auth.admin.createUser()` (عبر دالة سيرفر آمنة)
2. استبدال "تغيير كلمة المرور من الأدمن" بزر **"إرسال رابط إعادة تعيين"** (`sb.auth.resetPasswordForEmail()`)
3. حذف شاشة عرض/نسخ كلمة المرور (`index.html.html:20387-20392`)
4. تعديل تسجيل الدخول ليعتمد على `sb.auth.signInWithPassword()` بدل `verify_login`

### المرحلة 1ب — ترحيل المستخدمين الحاليين (SQL على Staging)
5. سكربت يستخرج المستخدمين بلا `auth_id`
6. لكل واحد: إنشاء حساب Auth + ربط `auth_id` + إرسال دعوة تعيين كلمة مرور
7. **لا تُنقل كلمة المرور النصية إلى Auth** — يُطلب تعيين جديدة

### المرحلة 1ج — الحذف النهائي (SQL على Staging ثم Production لاحقًا)
8. التأكد أن صفر كتابات جديدة على `password_plain`
9. `ALTER TABLE users DROP COLUMN password_plain;`
10. حذف/تعطيل `verify_login` RPC (لم تعد مطلوبة)

## ملفات ستُنشأ لهذا الحاجز
- `security-fix-1a-auth-migration.sql` — إنشاء حسابات Auth للموجودين
- `security-fix-1b-drop-password-plain.sql` — حذف العمود + verify_login
- تعديلات على `index.html.html` (مسارات الدخول/الإضافة/التغيير)

# 🔴 B2 — تقييد CORS + مصادقة الـAPI

## أين المشكلة الآن

| الملف | السطر | المشكلة |
|-------|-------|---------|
| `api/agent.js` | 60 | `Access-Control-Allow-Origin: *` |
| `api/rewrite.js` | 6 | `Access-Control-Allow-Origin: *` |
| كلاهما | — | لا تحقق من Bearer token / JWT |

## خطوات التنفيذ

1. **Allowlist للدومين:**
   ```js
   const ALLOWED = ['https://shouon-al-ghithaa.vercel.app', 'http://localhost:3001'];
   const origin = req.headers.origin;
   if (ALLOWED.includes(origin)) res.setHeader('Access-Control-Allow-Origin', origin);
   ```
2. **التحقق من Supabase JWT:**
   - العميل يرسل `Authorization: Bearer <access_token>`
   - السيرفر يتحقق من التوكن عبر Supabase قبل استدعاء Gemini
3. **Rate limiting** بسيط (عدد طلبات/دقيقة لكل مستخدم)

## ملفات ستُعدَّل
- `api/agent.js`
- `api/rewrite.js`
